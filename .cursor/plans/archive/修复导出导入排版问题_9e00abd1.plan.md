# 修复 DOCX 导出/导入与编辑器排版问题

## 问题 1：标题导出到 DOCX 后变蓝色

### 根因

[docModelToDocx.ts](src/views/training/document/utils/docModel/docModelToDocx.ts) 的 `buildHeading` 函数（213-228 行）只传了 `heading` 级别，没有为 heading 的文本 runs 设置字体颜色：

```213:228:e:\job-project\collabedit-fe\src\views\training\document\utils\docModel\docModelToDocx.ts
const buildHeading = (block: DocHeadingBlock): Paragraph => {
  const headingMap: Record<number, any> = {
    1: HeadingLevel.HEADING_1,
    // ...
  }
  return createParagraph(block.runs, {
    align: block.style?.align,
    spacing: paragraphSpacing(block),
    indent: paragraphIndent(block),
    heading: headingMap[block.level] || HeadingLevel.HEADING_1
  })
}
```

`docx` 库使用 Word 的 `HeadingLevel` 样式时，Word 内置 Heading 1-6 的默认字体颜色是蓝色主题色（如 `#2F5496`），而编辑器中的 CSS 分别设置了 h1: `#111827`、h2: `#1f2937`、h3: `#374151`。由于 `DocRun` 中没有 `style.color`，导出时不会覆盖 Word 的主题色，最终显示为蓝色。

### 修复方案

在 `buildHeading` 中，对没有显式 `style.color` 的 runs 注入与编辑器 CSS 一致的默认颜色：

- **文件**: [docModelToDocx.ts](src/views/training/document/utils/docModel/docModelToDocx.ts)
- **修改**: 在 `buildHeading` 中，遍历 `block.runs`，对 `run.style?.color` 为空的 run，根据 `block.level` 注入默认黑色。使用映射表：

```typescript
const headingColorMap: Record<number, string> = {
  1: '#111827',
  2: '#1f2937',
  3: '#374151',
  4: '#374151',
  5: '#4b5563',
  6: '#4b5563'
}
```

在 `createParagraph` 调用前，做一次 runs 映射，为无色 run 填充默认颜色。

## 问题 2：块图片下方多出一行

### 根因

当 `appendTransaction` 将块图片拆分为独立段落 `paragraph([image])` 后，ProseMirror 会在该段落末尾自动插入 `<br class="ProseMirror-trailingBreak">`，结构为：

```html
<p>
  <div class="resizable-image-wrapper">...</div>
  <br class="ProseMirror-trailingBreak">
</p>
```

当前 CSS 只处理了 `::after`（隐藏 `↵`），但没有处理 `<br>` 本身。这个 `<br>` 在布局中占一行，导致块图片下方多出一个空行。

### 修复方案

- **文件**: [TiptapEditor.vue](src/views/training/document/components/TiptapEditor.vue)
- **修改**: 在现有 `p` 样式块中，对含块图片段落的 `trailingBreak` 做视觉折叠。不能用 `display: none`（会破坏光标定位），而是用 `font-size: 0; line-height: 0; height: 0;` 让 `<br>` 不占视觉空间但保持在 DOM 流中：

```scss
// 含块图片的段落：折叠 trailingBreak，避免多出一行
&:has(> .resizable-image-wrapper:not(.is-inline)) > br.ProseMirror-trailingBreak {
  font-size: 0;
  line-height: 0;
  height: 0;
  overflow: hidden;
  display: block;
}
```

放在已有的 `&:has(> .resizable-image-wrapper:not(.is-inline))::after { content: none; }` 规则之后。

## 问题 3：DOCX 导入丢失行内图片

### 根因

[docx4jsParser.ts](src/views/training/document/utils/docModel/docx4jsParser.ts) 的 `collectRunsFromTree`（250-301 行）负责从段落树中收集 `DocRun`，但**没有处理 `img` 标签**。当段落内出现 `<img>` 时：

```250:301:e:\job-project\collabedit-fe\src\views\training\document\utils\docModel\docx4jsParser.ts
const collectRunsFromTree = (node: DocxTreeChild, inherited?: RunStyle): DocRun[] => {
  // ... 处理 a, br, footnote, endnote, strong, em, u, s, sup, sub, mark
  const children = element.children || []
  return children.flatMap((child) => collectRunsFromTree(child, nextStyle))
}
```

`<img>` 是 void 元素（无子节点），`children.flatMap(...)` 返回空数组，行内图片被丢弃。

同时，`parseBlocksFromTree`（442-465 行）中 `tag === 'img'` 分支只调用 `parseImageFromTree` 生成 `DocImageBlock`，但这只处理块级 `<img>`。当 `<img>` 出现在 `<p>` 内部（作为行内图片）时，它被 `collectRunsFromTree` 处理——然后被丢弃。

### 修复方案

- **文件**: [docx4jsParser.ts](src/views/training/document/utils/docModel/docx4jsParser.ts)
- **修改**: 在 `collectRunsFromTree` 中增加 `tag === 'img'` 分支，将行内图片解析为带 `image` 字段的 `DocRun`：

```typescript
if (tag === 'img') {
  const props = element.props || {}
  const styleText = typeof props.style === 'string' ? props.style : styleToText(props.style)
  const styleMap = styleText ? extractStyleMap(styleText) : {}
  return [
    {
      text: '',
      image: {
        src: String(props.src || ''),
        alt: props.alt ? String(props.alt) : undefined,
        width: parsePxValue(props.width) || parsePxValue(styleMap['width']),
        height: parsePxValue(props.height) || parsePxValue(styleMap['height'])
      },
      style: inherited
    }
  ]
}
```

插入位置：在 `if (tag === 'br')` 分支之后、样式标签处理之前。

### 影响范围检查

- `serializeRun` 已支持 `run.image`，会正确输出 `<img data-display="inline">`
- `mapRunToRuns` 已支持 `run.image`，DOCX 导出正确
- 类型 `DocRun.image?: DocInlineImage` 已定义
- 不影响块级图片处理（`parseBlocksFromTree` 中 `tag === 'img'` 仍走 `parseImageFromTree`）
