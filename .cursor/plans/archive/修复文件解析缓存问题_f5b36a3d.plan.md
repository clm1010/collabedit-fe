# 修复文件解析缓存与内容不一致问题

## 问题根因分析

### 根因 1：IndexedDB 陈旧缓存 -- 最高优先级

在 [TiptapCollaborativeEditor.vue](e:\job-project\collabedit-fe\src\views\training\document\TiptapCollaborativeEditor.vue) 的 `onMounted` 中（约 1136-1158 行），当前逻辑：

```
if (hasStyleHintsInHtml(parsedContent)) {
  // 有样式 -> 缓存到 IndexedDB
  preloadedContent = parsedContent
  setDocCache(docId, parsedContent)
} else {
  // 无样式 -> 尝试从 IndexedDB 恢复带样式的缓存版本（可能是 7 天内的旧数据！）
  const cachedHtml = await getDocCache(docId)
  if (cachedHtml && hasStyleHintsInHtml(cachedHtml)) {
    preloadedContent = cachedHtml  // BUG：用旧内容替换了新解析结果
  }
}
```

**致命场景**：

1. 用户首次打开文档 A -> DocModel 解析带样式 -> 缓存到 IndexedDB
2. 用户编辑文档 A 并保存（HTML -> DOCX 转换，写入 MinIO）
3. 用户再次打开文档 A -> `getFileStream` 拿到新 DOCX -> `parseFileContent` 解析
4. 如果新解析碰巧走了不带样式的路径（如 Mammoth fallback），触发 `else` 分支
5. 从 IndexedDB 取出**步骤 1 的旧内容**，覆盖了新解析结果 -- **内容不一致！**

**多用户致命场景**：

1. 用户 A 打开文档 X -> 缓存到 IndexedDB
2. 用户 B 通过协同编辑修改文档 X 并保存 -> MinIO 中的 DOCX 已更新
3. 用户 A 再次打开文档 X -> `getFileStream` 拿到 B 修改后的新 DOCX
4. 如果新解析无样式 -> 回退到 IndexedDB 中 A 的旧缓存 -> **显示的是修改前的旧内容！**

Fix 1（保存清缓存）只能解决自己保存的场景，无法覆盖多用户场景，因此 Fix 2（移除旧缓存回退）是必要的。

### 根因 2：保存后未清除 IndexedDB 缓存

`handleSave()` 成功后（约 1007 行），只更新了 `hasUnsavedChanges` 和 `documentInfo.updateTime`，**没有调用 `deleteDocCache(documentId.value)`** 来清除旧缓存。下次打开时旧缓存仍然有效。

### 根因 3：解析策略非确定性

`parseFileContent`（[wordParser.pipeline.ts](e:\job-project\collabedit-fe\src\views\training\document\utils\wordParser.pipeline.ts)）的多策略 fallback 在以下情况可能产生不同输出：

- DocModel 成功但无样式 -> 尝试 OOXML Enhanced
- OOXML Enhanced 失败 -> 回退到无样式的 DocModel 结果
- 最终 Mammoth fallback -> 完全不同的 HTML

每次解析可能因内部状态或 Worker 时序不同而命中不同路径。

### 关于重复调用 getFileStream

在正常流程中**不会重复调用**：

- 列表页 `handleEdit` 调用一次 -> 存入 `docBufferStore`（Pinia 内存 store）
- 编辑器 `onMounted` 优先从 `docBufferStore.getBuffer()` 读取
- 仅在页面刷新（内存 store 被清空）时才会再次调用

但后端未设置 `Cache-Control` 响应头，建议补上 `no-store` 以避免浏览器/代理缓存干扰。

## 修复方案

### Fix 1：保存成功后清除 IndexedDB 缓存

文件：[TiptapCollaborativeEditor.vue](e:\job-project\collabedit-fe\src\views\training\document\TiptapCollaborativeEditor.vue)

在 `handleSave()` 成功的 `if` 分支（约 1007-1015 行），`hasUnsavedChanges.value = false` 之后添加：

```typescript
void deleteDocCache(documentId.value)
```

确保保存后旧缓存被清除，下次打开时必然使用新解析结果。

**影响分析**：`deleteDocCache` 是异步 fire-and-forget（`void` 前缀），失败时会被 try-catch 吞掉，不影响保存流程。`handleSave` 也被 `performAutoSave` 调用，因此自动保存也会正确清除缓存。

### Fix 2：移除 IndexedDB 旧缓存回退 -- 始终使用最新解析结果

文件：[TiptapCollaborativeEditor.vue](e:\job-project\collabedit-fe\src\views\training\document\TiptapCollaborativeEditor.vue)

修改 `onMounted` 中约 1145-1158 行的 `else` 分支。

**当前逻辑**：解析结果无样式 -> 从 IndexedDB 取旧缓存替代 **改为**：始终使用最新解析结果，不再回退到旧缓存。

```typescript
if (hasStyleHintsInHtml(parsedContent)) {
  preloadedContent.value = parsedContent
  void setDocCache(documentId.value, parsedContent)
  logger.debug('预加载内容解析成功（含样式），已缓存到 IndexedDB，HTML 长度:', parsedContent.length)
} else {
  preloadedContent.value = parsedContent
  logger.debug('预加载内容解析成功（无样式），使用当前结果，HTML 长度:', parsedContent.length)
}
```

**影响分析**：

- 正向：彻底消除陈旧缓存覆盖新内容的问题，包括多用户协同场景
- 正向：`setDocCache` 仍在有样式时写入，保持数据累积，为将来可能的优化预留
- 代价：如果解析走了无样式路径（如 Mammoth fallback），用户看到的内容可能缺少字体/颜色等样式
- 可接受性：**内容正确性 > 样式完整性**，编辑器自身 CSS 会提供基础排版，且 `applyPreloadedContent` 的重试机制（第 924 行）会尝试恢复样式

### Fix 3：后端 getFileStream 添加 Cache-Control 响应头

文件 1：[training.ts](e:\job-project\collabedit-node-backend\src\routes\training.ts) 约 87 行文件 2：[template.ts](e:\job-project\collabedit-node-backend\src\routes\template.ts) 约 88 行

在两个路由的 `res.setHeader('Content-Type', ...)` 之后添加：

```typescript
res.setHeader('Cache-Control', 'no-store, no-cache, must-revalidate')
res.setHeader('Pragma', 'no-cache')
```

**影响分析**：

- 前端 axios 的 GET 请求拦截器已添加 `Cache-Control: no-cache` 和 `Pragma: no-cache`（javaService.ts 第 76-78 行），但这只是请求头
- 响应头的 `Cache-Control` 才是浏览器/中间代理/CDN/Nginx 真正遵守的缓存指令
- `no-store` 确保浏览器不存储响应，`must-revalidate` 确保过期缓存不被使用
- 不影响其他接口，仅对文件流下载生效

### Fix 4：降低 IndexedDB 缓存有效期至 24 小时

文件：[TiptapCollaborativeEditor.vue](e:\job-project\collabedit-fe\src\views\training\document\TiptapCollaborativeEditor.vue) 第 189 行

```typescript
// 修改前
const DOC_CACHE_EXPIRE_MS = 7 * 24 * 60 * 60 * 1000 // 7 天过期

// 修改后
const DOC_CACHE_EXPIRE_MS = 24 * 60 * 60 * 1000 // 24 小时过期
```

**影响分析**：

- 组件挂载时 `cleanExpiredDocCache()`（第 1170 行）会清理过期条目，24h TTL 让过期条目更快被清理
- 配合 Fix 1（保存清缓存）和 Fix 2（不回退旧缓存），形成三重防护
- 即使 Fix 1 因某种原因未执行（如网络中断导致保存失败），24h 后缓存也会自动失效

## 关于 getFileStream 重复调用的结论

经过全链路排查确认：

- **列表页 -> 编辑器**的正常 SPA 导航中只调用 1 次（列表页 `handleEdit` 调用后存入 `docBufferStore`，编辑器优先从内存读取）
- **页面刷新**时会再调用 1 次（`docBufferStore` 是 Pinia 内存 store，刷新后清空，这是预期行为）
- `**watch(documentId)` 监听中不调用 `getFileStream`，只做 `loadDocument` + `reinitializeCollaboration`
- 无需修改调用逻辑

## 不涉及的部分

- 中间件 (`collaborative-middleware`)：不参与 `getFileStream` 请求，只处理 WebSocket 协同
- MinIO 存储层：`getFileStream` 直接从 MinIO 读取最新 object，无自身缓存
- `docBufferStore`（Pinia 内存 store）：页面刷新后自动清空，不存在持久化缓存问题
- 前端 HTTP 请求拦截器：GET 请求已有 `Cache-Control: no-cache` 请求头，无需修改

## 安全性评审

- Fix 1-4 均为**前端/后端独立修改**，互不依赖，可单独部署
- Fix 1: 仅在保存成功分支执行，失败不影响保存流程
- Fix 2: 仅改变缓存回退策略，不影响正常解析流程和协同同步逻辑
- Fix 3: 仅添加响应头，不改变接口行为
- Fix 4: 仅改变常量值，`cleanExpiredDocCache` 已有对该值的引用
- 所有修改不影响编辑器内容编辑、协同同步、自动保存、文档导入导出等现有功能
